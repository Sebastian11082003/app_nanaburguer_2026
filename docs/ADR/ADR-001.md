# ADR-001 — Architectural Style Decision

| Campo                        | Detalle                               |
| ---------------------------- | ------------------------------------- |
| **Estado**                   | ✅ Accepted                           |
| **Fecha**                    | 2026-05-10                            |
| **Autor**                    | NanaBurger SaaS Team                  |
| **Decisor**                  | Arquitectura del Proyecto             |
| **Patrón / Principio**       | Modular Monolith + Clean Architecture |
| **Impacto arquitectónico**   | Crítico                               |
| **Módulos afectados**        | Todo el sistema                       |
| **Tecnologías relacionadas** | NestJS, Prisma, PostgreSQL, Docker    |

---

# Contexto

NanaBurger inició como un MVP rápido enfocado en:

- gestión de pedidos,
- mesas,
- pagos,
- operación básica de restaurante.

Durante el desarrollo el sistema evolucionó significativamente hacia una plataforma SaaS preparada para:

- escalabilidad,
- modularidad,
- despliegue cloud,
- múltiples integraciones futuras,
- crecimiento multi-sucursal,
- expansión multi-tenant.

---

# Problema

¿Cómo diseñar una arquitectura que permita:

- desarrollar rápidamente el MVP,
- mantener una estructura escalable,
- reducir acoplamiento,
- facilitar mantenimiento,
- permitir crecimiento futuro,
- minimizar complejidad operacional?

---

# Drivers Arquitectónicos

| Driver               | Prioridad |
| -------------------- | --------- |
| Maintainability      | Alta      |
| Modularidad          | Alta      |
| Escalabilidad futura | Alta      |
| Bajo overhead DevOps | Alta      |
| Rapidez MVP          | Alta      |
| Cloud readiness      | Alta      |
| Evolución SaaS       | Alta      |

---

# Opciones Consideradas

## Opción 1 — Monolito Tradicional

### Beneficios

| ✅ Beneficios            |
| ------------------------ |
| Desarrollo rápido        |
| Baja complejidad inicial |
| Fácil onboarding         |

### Problemas

| ❌ Problemas           |
| ---------------------- |
| Alto acoplamiento      |
| Escalabilidad limitada |
| Technical debt         |

---

## Opción 2 — Microservices

### Beneficios

| ✅ Beneficios               |
| --------------------------- |
| Escalabilidad independiente |
| Despliegues desacoplados    |
| Aislamiento de dominios     |

### Problemas

| ❌ Problemas            |
| ----------------------- |
| Complejidad DevOps      |
| Overengineering         |
| Mayor costo operacional |

---

## Opción 3 — Modular Monolith + Clean Architecture

### Beneficios

| ✅ Beneficios          |
| ---------------------- |
| Modularidad clara      |
| Bajo overhead          |
| Escalable              |
| Cloud-ready            |
| Fácil migración futura |

### Problemas

| ❌ Problemas                    |
| ------------------------------- |
| Más boilerplate                 |
| Mayor disciplina arquitectónica |

---

# Decisión

Se adopta:

# Modular Monolith + Clean Architecture

como arquitectura oficial del sistema.

---

# Arquitectura Definida

## Domain Layer

- entidades,
- enums,
- reglas de negocio.

## Application Layer

- casos de uso,
- interfaces,
- contratos.

## Infrastructure Layer

- Prisma ORM,
- PostgreSQL,
- adapters.

## Interface Layer

- REST Controllers,
- Swagger,
- JWT,
- RBAC.

---

# Beneficios Arquitectónicos

| ✅ Beneficios         | ⚠️ Trade-offs     |
| --------------------- | ----------------- |
| Escalabilidad modular | Más boilerplate   |
| Fácil testing         | Mayor disciplina  |
| Cloud-ready           | Más complejidad   |
| Evolución SaaS        | Curva aprendizaje |

---

# Riesgos

| Riesgo                     | Mitigación             |
| -------------------------- | ---------------------- |
| Acoplamiento entre módulos | Dependency inversion   |
| Layer leakage              | Code reviews           |
| Violación arquitectura     | Convenciones estrictas |
