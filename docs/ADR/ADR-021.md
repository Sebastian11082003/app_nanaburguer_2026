# ADR-021: Sesiones de caja (CashSession)

| Campo | Detalle |
|-------|---------|
| Estado | ACCEPTED |
| Fecha | 2026-08-12 |
| Versión producto | v0.5.0 |
| Decisión | Una sesión de cajón por restaurante; movimientos y cobros CASH se amarran a ella |

---

## Contexto

El POS ya registraba `CashMovement` al cobrar en efectivo, pero sin
turno/sesión no había:

- base de apertura,
- egresos tipados del día,
- arqueo (esperado vs contado),
- historial de cierres.

Feedback senior: un SaaS de restaurante profesional necesita caja
operativa antes de inventario y contabilidad completa.

## Decisión

Introducir `CashSession` (OPEN | CLOSED) con:

- `openingFloatCents`
- movimientos hijos (`CashMovement.sessionId`)
- al cierre: `expectedCashCents`, `countedCashCents`, `differenceCents`

Reglas:

1. Máximo una sesión OPEN por `restaurantId`.
2. Movimientos manuales requieren sesión OPEN.
3. `PaymentMethod.CASH` exige sesión OPEN; crea `SALE_PAYMENT` en esa sesión.
4. CARD/TRANSFER no generan movimiento de cajón.

## Alternativas rechazadas

- **Caja implícita por día calendario:** frágil con turnos nocturnos.
- **Multi-caja desde el día 1:** se difiere; el modelo permite extender
  con `stationId` / `registerId` después.
- **Contabilidad completa en esta fase:** se deja para fases posteriores
  (exportación / plan de cuentas).

## Consecuencias

- Flujo de cobro en efectivo depende de abrir caja (UX cajero/admin).
- Inventario/compras deberán referenciar egresos de caja o crear
  `Purchase` aparte (fase 2–4).
- Documentación obligatoria: ver
  `docs/ops/documentation-checklist-financial.md`.
